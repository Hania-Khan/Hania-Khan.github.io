JazzCash · Payments platform

Scaling payment throughput from ~200 to 800 TPS

I set TPS targets for each module from screen-level call volumes and active-user data, worked out with the Data Analytics team. Then I worked through the bottlenecks layer by layer: API, middleware and database.

  • Caching at the application and integration layers for read-heavy lookups, so repeated calls stopped hitting core systems.
  • Horizontal scaling and load balancing for high-volume modules, adding nodes against the sized TPS rather than over-provisioning.
  • Asynchronous hand-off through Kafka and Red Hat AMQ for work that didn't need to block the customer journey.
  • Load testing against the targets before each release, with ELK-based observability in production.

JazzCash · Partner onboarding

A reusable pattern for third-party integrations

I onboarded 8+ partners across insurance, payments, lending and campaign management. The first few were one-off builds. After that I turned the common parts into a pattern later partners could follow: a contract-first API spec, mediation and transformation in WSO2 Micro Integrator, consistent error mapping, and agreed TPS and timeout budgets per partner.

For each project I wrote the Functional Requirement Specification and produced the infrastructure cost estimate and TPS calculation, so business and engineering signed off on the same numbers.
