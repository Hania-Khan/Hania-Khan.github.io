How I work

Start from the requirement

I pin down scope and performance targets with the business before writing code, so what I build is what was needed.

Test it before it ships

Design for integration

Contract-first APIs, consistent error handling and agreed timeout budgets make external systems predictable to build against.

Stay with it in production

Observability, incident response and root-cause analysis are part of the job. I'd rather fix the cause than keep closing the same ticket.

JazzCash · Platform performance

Scaling a high-traffic platform from ~200 to 800 TPS

I set TPS targets for each module from screen-level call volumes and active-user data, worked out with the Data Analytics team. Then I worked through the bottlenecks layer by layer: API, middleware and database.

  • Caching frequently used data in Redis, so repeated calls stopped hitting core systems.
  • Optimising slow MySQL and MongoDB queries on the busiest journeys.
  • Scaling Node.js services horizontally on OpenShift, adding nodes against the sized TPS rather than over-provisioning.
  • Asynchronous hand-off through Kafka and Red Hat AMQ for work that didn't need to block the customer journey.
  • Worked with the Data Analytics team on screen-level call volumes to decide how many features a screen could carry without slowing it down.
  • Load testing against the targets before each release, with ELK-based observability in production.

JazzCash · Partner onboarding

A reusable pattern for third-party integrations

I integrated 8+ insurance, lending and payment partners using JavaScript/TypeScript REST APIs, with Kafka events for transaction status updates. The first few were one-off builds. After that I turned the shared code into reusable templates, covered by automated tests and Postman collections, so each new partner was faster and more consistent to onboard. API contracts were agreed with each partner before go-live, with mediation in WSO2 Micro Integrator and agreed TPS and timeout budgets.

For each project I wrote the Functional Requirement Specification and produced the infrastructure cost estimate and TPS calculation, so business and engineering signed off on the same numbers.

JazzCash · Finance & planning

CAPEX portal

Infrastructure spending at JazzCash was tracked in an error-prone Excel workbook used by senior leadership and project managers. I built the CAPEX Management portal end to end to replace it, so planners, leadership (including the CEO and CTO) and project managers have one place to see what has been budgeted, approved and spent, project by project.

  • Dashboards showing spend against budget across projects, so leadership can see where funds stand at a glance.
  • Approval workflows that move requests through the right approvers in order, with each step recorded.
  • Validated forms for raising and updating requests, with the business rules checked on both the client and the server.
  • Budget and expenditure history per project, with reports generated from the same data.
  • Data tables with filtering and sorting for working through large sets of projects and line items.
  • Role-based dashboards and access, so planners, project managers and executives each see and act on only what their role allows.
  • Two-factor login and a full audit trail, so every change and approval can be traced.
